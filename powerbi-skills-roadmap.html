week 3–6
Data modeling
B1✓ mastered30 mintap ▸
Build relationships and a star schema
Before you drag a single relationship, answer one question: "what does one row in this fact table represent?" That's the table's grain — one sale line, one shipment, one login. Get the grain wrong and every measure built on top inherits the mistake. Once the grain is clear, keys and cardinality follow naturally, and a real data model — one fact table surrounded by dimension tables — is what lets Power BI slice correctly by any field you throw at it, instead of one flattened Excel export.
Ask first: "one row = ?" (e.g. one row = one order line, not one order) Model view → drag a key field from the fact table to the matching dimension table Set cardinality (usually one-to-many) and cross-filter direction (usually single)
Star schema — one fact table, several dimensions
B2✓ mastered25 mintap ▸
Merge and Append queries in Power Query
Merge joins two tables side-by-side on a matching key (like a lookup table). Append stacks tables with the same columns on top of each other. Mixing the two up is the most common Power Query mistake.
Home → Merge Queries — pick the matching key column in each table (like a SQL join) Home → Append Queries — stacks rows from tables with the same structure (like a SQL union)
Power Query deep dive
B7✓ mastered20 mintap ▸
Data types, and clean shaping (rename, reorder, remove)
Every downstream step — date math, sorting, aggregation, a merge on a key — assumes the column's data type is right. Fixing type, name, and column order early, right after connecting, is what keeps later steps from silently breaking.
Column header icon (ABC / 123 / calendar) → Change Type Right-click a column → Rename, Remove, or Move → to reorder without dragging
B8✓ mastered25 mintap ▸
Conditional columns, custom columns, and Group By
A Conditional Column builds if/then/else logic through a dialog — faster and less error-prone than hand-written M for simple branching. A Custom Column is for real M expressions. Group By collapses rows into per-category summaries, the Power Query equivalent of a SQL GROUP BY.
Add Column → Conditional Column — if/then/else, no M required Add Column → Custom Column — for anything a dialog can't express Transform → Group By — pick a key column, then an aggregation (Sum, Count, Average…)
B9✓ mastered25 mintap ▸
Unpivot/Pivot and query parameters
Source data often arrives wide — one column per month or category — when Power BI wants it long, one row per observation. Unpivot fixes that shape in a couple of clicks. Parameters let you swap a hardcoded value (a file path, a date, an environment) for a variable other queries can reference, so one file can point at dev or prod without editing every step.
Select the category columns → Transform → Unpivot Columns (wide → long) Manage Parameters → New Parameter → reference it inside a query's Source step
B10✓ mastered25 mintap ▸
Query dependencies, references, and error handling
Referencing one query from another (instead of duplicating it) means a single upstream fix flows everywhere — but only if you can see who depends on whom before you rename or delete something. Try/otherwise and error-aware steps stop one bad row from failing an entire refresh.
View → Query Dependencies — see the full reference tree before changing a shared query Right-click a query → Reference (not Duplicate) to build on it without copying its steps try [Column] otherwise null — catch a row-level error instead of failing the whole query
First DAX
B11✓ mastered20 mintap ▸
Implicit vs. explicit measures, and DIVIDE
Dragging a raw numeric field into a visual and letting Power BI auto-sum it creates an implicit measure — it works, but it's invisible, uneditable as its own object, and breaks field parameters later. An explicit measure — one you name and write yourself — is the professional default. DIVIDE is the other habit to build immediately: a plain a/b expression errors or shows an ugly infinity the moment the denominator is zero or blank; DIVIDE handles that gracefully with a fallback.
Implicit (avoid as a habit): dragging Sales[Amount] straight into a card, auto-summed Explicit (prefer): Total Sales = SUM(Sales[Amount]) Avg Order Value = DIVIDE([Total Sales], [Order Count], 0) — returns 0 instead of an error when Order Count is 0
B3✓ mastered30 mintap ▸
Measures vs. calculated columns, and CALCULATE
A measure recalculates live for whatever's currently filtered; a calculated column is baked in row-by-row at refresh time. Once you're writing explicit measures, CALCULATE is the next step: it's how you deliberately change the filter context a measure sees, rather than accepting whatever's already on the page.
Total Sales = SUM(Sales[Amount]) Sales in EU = CALCULATE([Total Sales], Geography[Region] = "EU")
B4✓ mastered20 mintap ▸
Matrix, drillthrough pages, and bookmarks
A matrix is your pivot-table-style visual. Drillthrough sends users to a detail page filtered to whatever they clicked. Bookmarks save a specific view — filters, visibility, all of it — so you can replay it with one click.
Matrix visual → drag fields into Rows, Columns, Values Format pane → set a "Drillthrough" target field on the detail page View → Bookmarks pane → Add, to capture the current state
Dates & relationships
B5✓ mastered25 mintap ▸
Build a real Calendar table; turn off Auto Date/Time
Auto Date/Time quietly creates a hidden calendar per date column — fine for a demo, but it multiplies hidden tables and breaks the moment you need one shared calendar for time intelligence. This is a common stumbling block right before time intelligence.
File → Options → Data Load → uncheck "Auto Date/Time" (do this before building anything) New Table: Calendar = CALENDAR(DATE(2023,1,1), DATE(2026,12,31)) Add Year / Month / Quarter columns, then Mark as Date Table
B6✓ mastered25 mintap ▸
Troubleshoot relationships (inactive, many-to-many, ambiguous paths)
More than one live path between two tables makes the model ambiguous, so Power BI keeps only one relationship active. Recognizing an inactive relationship, or a many-to-many that needs a bridge table, is what stops numbers from silently coming out wrong.
Model view → dashed line = inactive relationship USERELATIONSHIP() activates an inactive relationship for just one measure: Sales (Ship Date) = CALCULATE([Total Sales], USERELATIONSHIP(Sales[ShipDate], 'Date'[Date])) True many-to-many? Add a bridge table with unique keys instead of linking the two tables directly

Developer

week 7–11
DAX: filter context & variables
C3✓ mastered20 mintap ▸
VAR / RETURN for readable DAX
Variables stop you repeating the same sub-expression twice, and they make a formula something you can actually debug line by line instead of untangling nested parentheses. Reach for VAR/RETURN the moment a measure needs more than one step.
Avg Line Value = VAR TotalAmt = SUM(Sales[Amount]) VAR TotalQty = SUM(Sales[Qty]) RETURN DIVIDE(TotalAmt, TotalQty)
C2✓ mastered35 mintap ▸
Filter modifiers: ALL, ALLEXCEPT, ALLSELECTED
These control which filters CALCULATE ignores or keeps — the core mechanic behind "% of total" and the ranking patterns you'll build later.
% of Total = DIVIDE([Total Sales], CALCULATE([Total Sales], ALL(Sales))) Keeps Region filter, drops everything else: CALCULATE([Total Sales], ALLEXCEPT(Sales, Sales[Region]))
C1✓ mastered35 mintap ▸
Date intelligence: TOTALYTD, SAMEPERIODLASTYEAR
Year-to-date and year-over-year comparisons only work reliably against a proper, contiguous calendar table — marked as an official date table, not just any date column.
YTD Sales = TOTALYTD([Total Sales], 'Date'[Date]) Sales LY = CALCULATE([Total Sales], SAMEPERIODLASTYEAR('Date'[Date])) Model view → right-click the Date table → Mark as Date Table
CALCULATE modifying filter context
Model & security
C4✓ mastered30 mintap ▸
Row-level security (RLS)
RLS restricts which rows a signed-in user can see, based on their identity — one report, no duplicated versions per team or region.
Modeling → Manage Roles → New role → add a table filter, e.g.: [Manager Email] = USERPRINCIPALNAME() Modeling → View As → test the role before publishing
Context, iteration & virtual tables
C5✓ mastered35 mintap ▸
Row context vs. filter context, and context transition
Row context is the row DAX is currently "standing on" — inside a calculated column or an iterator. Filter context is the set of filters from slicers, visuals, and CALCULATE. Context transition — CALCULATE turning a row context into an equivalent filter — is the single idea that explains why measures behave differently inside iterators.
Calculated column — row context only: Line Total = Sales[Qty] * Sales[UnitPrice] Inside an iterator, CALCULATE converts each row into a one-row filter (context transition): Customer Total = SUMX(Customer, CALCULATE([Total Sales])) — here CALCULATE filters Sales down to just that customer's rows, per iteration
C6✓ mastered25 mintap ▸
Iterator functions: SUMX, AVERAGEX, and friends
Iterators walk a table row by row, evaluating an expression at each row before aggregating — the only way to do row-level math, like quantity × price, that a plain SUM can't express.
Total Revenue = SUMX(Sales, Sales[Qty] * Sales[UnitPrice]) Avg Line Value = AVERAGEX(Sales, Sales[Qty] * Sales[UnitPrice]) MAXX, MINX, COUNTX follow the same pattern: table first, expression second
C11✓ mastered30 mintap ▸
FILTER, REMOVEFILTERS, and KEEPFILTERS
FILTER builds a virtual table by testing a condition row by row — the tool for filter logic ALLEXCEPT can't express. REMOVEFILTERS says exactly which filters to clear, in plain language — reach for it before ALL() when the goal is simply "ignore this filter," since ALL() also strips context in ways that surprise people using it for the first time. KEEPFILTERS does the opposite: it stops CALCULATE's default behavior of overwriting an existing filter, so a new condition narrows instead of replaces.
High Value Orders = CALCULATE([Order Count], FILTER(Sales, Sales[Amount] > 1000)) % of All Products = DIVIDE([Sales], CALCULATE([Sales], REMOVEFILTERS('Product'))) CALCULATE([Sales], KEEPFILTERS('Product'[Category] = "Bikes")) — narrows within the existing filter instead of replacing it
C10✓ mastered20 mintap ▸
SELECTEDVALUE and VALUES — reading the current selection
SELECTEDVALUE is one of the most common functions in real Power BI work: it returns a value only when a filter narrows a column to exactly one, and a fallback otherwise — perfect for a card title or a what-if input that should show "(multiple)" instead of guessing. VALUES returns the distinct values currently visible in the filter context as a one-column table, the building block underneath a lot of dynamic DAX.
Selected Product = SELECTEDVALUE('Product'[Name], "Multiple products") COUNTROWS(VALUES('Product'[Category])) — how many distinct categories are in view right now
C12✓ mastered30 mintap ▸
Virtual tables: SUMMARIZE and SUMMARIZECOLUMNS
Most real DAX beyond a simple measure involves building a table in memory — grouped rows with aggregates attached — and then doing something with it (ranking it, filtering it, iterating it). SUMMARIZECOLUMNS is the modern, faster way to do this; SUMMARIZE still shows up constantly in existing models and needs to be readable even if you default to SUMMARIZECOLUMNS in new work.
SUMMARIZECOLUMNS('Product'[Category], "Total Sales", [Sales], "Order Count", [Order Count]) SUMMARIZE(Sales, 'Product'[Category], "Total Sales", SUM(Sales[Amount])) — older pattern, still common in legacy models
C15✓ mastered30 mintap ▸
Ranking patterns: RANKX
RANKX puts every earlier Level 3 idea to work at once — it ranks a value against other rows in a virtual table, and that ranking table almost always needs ALL() wrapped around it so the rank doesn't reset inside every filter context (a row context / context transition issue) the moment it's dropped into a matrix.
Customer Rank = RANKX(ALL(Customer), [Total Sales], , DESC) Rank within Region = RANKX(ALLEXCEPT(Customer, Customer[Region]), [Total Sales], , DESC) — ranks within each region instead of globally
Performance & governance
C7✓ mastered30 mintap ▸
Performance Analyzer & Query Diagnostics
Performance Analyzer times every visual on a page — DAX query time vs. visual rendering time — so you know whether a slow report is a bad measure or just a busy canvas. Query Diagnostics goes a layer deeper, tracing what Power Query itself is doing during refresh.
View → Performance Analyzer → Start Recording → interact with the page Each visual reports DAX query / Visual display / Other time Power Query: Tools → Query Diagnostics → Start Diagnostics, then refresh a query
C9✓ mastered25 mintap ▸
Query folding
When your source supports it (most databases), Power Query can push your transformation steps back to the source as a generated query — a filter, a group by, a join — instead of pulling every row first and processing it locally. One step that can't fold (a custom column with an unsupported function, an early Table.Buffer) breaks folding for every step after it, silently turning a fast server-side query into a slow local one.
Right-click any step → "View Native Query" — greyed out means folding already broke upstream Keep filters, renames, and type changes near the top of a query; put custom M logic as late as possible
C8✓ mastered30 mintap ▸
Calculation groups (optional)
Without calculation groups, a time-intelligence toolkit — YTD, QTD, prior year, prior period — has to be rebuilt for every single measure. A calculation group applies the same set of DAX transforms across many measures at once. Calculation groups can now be created natively in Power BI Desktop's Model view — Tabular Editor is no longer required to get started, though it's still the faster tool for bulk edits, scripting, and advanced automation.
Model view → Calculation group button (ribbon) → creates the group natively in Desktop Tabular Editor remains useful for bulk-editing many calculation items at once, or scripting them Calculation group "Time Intelligence" with calculation items: YTD → CALCULATE(SELECTEDMEASURE(), TOTALYTD('Date'[Date], ...)) PY → CALCULATE(SELECTEDMEASURE(), SAMEPERIODLASTYEAR('Date'[Date]))
Interactive report design
C13✓ mastered25 mintap ▸
Field parameters
A field parameter lets a report viewer swap which measure or dimension a visual shows — "Sales vs. Profit vs. Quantity" as a slicer choice on the same chart — instead of you building a separate visual for every combination. It behaves like a small table of its own, so it interacts with explicit measures, drillthrough, and tooltips slightly differently than a normal field; test those before shipping one.
Modeling → New Parameter → Fields — pick the measures/columns viewers can switch between Drop the resulting field onto a chart's axis or a slicer, exactly like a normal field Check drillthrough and tooltip pages still work correctly once a field parameter drives the visual
C14✓ mastered35 mintap ▸
Design an interactive report experience
A dashboard people can actually navigate — not just look at once — needs more than a matrix and a bookmark. Buttons and page navigators give structure; report-page tooltips add context without leaving the page; conditional formatting and dynamic titles make a report respond to what's selected; and checking the layout at a smaller width catches a report that only works on your monitor.
Insert → Buttons → Back/Bookmark/Page navigation — wire a button to a bookmark or another page Format a tooltip page at a small canvas size, then set it as another visual's tooltip in Format → Tooltip Conditional formatting → Format by rules or a measure (e.g. red under target, green over) Dynamic title = "Sales — " & SELECTEDVALUE('Date'[Year], "All years") File → Options → Mobile layout — arrange visuals for a phone view separately from the desktop canvas
Business thinking
C16✓ mastered20 mintap ▸
Requirements gathering: audience, decisions, and grain
The most expensive rework in Power BI is rarely a bad DAX formula — it's building the wrong report because nobody asked who it's for and what they'll actually do with it. Before opening Power BI, get clear answers on: who's the audience, what decision(s) will they make, which KPIs matter, what's the required grain, which filters are truly needed, and how fresh does the data need to be.
Audience: who opens this report, and how often? Decision: what will they do differently because of this number? Grain, filters, and refresh cadence: confirm all three before the first visual gets built
C17✓ mastered20 mintap ▸
KPI design: definition, numerator/denominator, and exceptions
A KPI isn't real until you can state its numerator, its denominator, and every business rule and exception that changes what counts — a return that shouldn't count against on-time delivery, a trial account that shouldn't count as a paying customer. Agree on the definition, the target, and the exceptions with the business before writing a single measure.
On-Time % → numerator: orders delivered by promised date; denominator: all orders; exception: customer-requested reschedules excluded Write the definition down somewhere the business can see and challenge it, before building the DAX
C18✓ mastered20 mintap ▸
Data validation and reconciliation
A dashboard that "looks about right" isn't validated. Before shipping, reconcile totals against the source system, check for duplicate rows introduced by a merge or relationship, and account for missing or null data instead of letting it silently vanish from a sum.
Compare the report's grand total against a source-system export or SQL query for the same period COUNTROWS(table) before vs. after a merge — catch duplication early Check a null/blank category doesn't just disappear from a bar chart's total
C19✓ mastered20 mintap ▸
Storytelling: executive summary → diagnostic → detail → action
A report a viewer can navigate is not the same as a report that tells them something. Structure pages in layers: an executive summary that answers the main question in five seconds, a diagnostic layer for "why," a detail layer for the row-level data, and a clear next action — not just a wall of charts in whatever order you built them.
Page 1 — Executive summary: the 3–5 numbers that matter, headline-first Page 2 — Diagnostic: breakdowns and trends that explain the headline Page 3 — Detail: the underlying table for anyone who needs to drill in Every page should end with an implied or explicit "so what do I do about it?"

Core production skills
D2✓ mastered30 mintap ▸
Composite models: Import, DirectQuery, Dual
Mixing storage modes per table lets you balance freshness against performance — import the small stable dimensions, DirectQuery the huge fact table that changes every minute.
Model view → select a table → Properties pane → Storage mode Import: fastest, cached snapshot DirectQuery: always live, queries the source Dual: can act as either, depending on the query
D3✓ mastered30 mintap ▸
Incremental refresh
Incremental refresh only reloads recent partitions instead of the entire fact table every night — a huge win for refresh time and source load once a fact table gets into the millions of rows.
Desktop → right-click a fact table → Incremental refresh policy → set a date range Requires Premium, PPU, or Fabric capacity in the service to actually run as configured on a schedule
D10✓ mastered25 mintap ▸
Deployment pipelines & ALM
Incremental refresh is a model/refresh optimization; deployment pipelines are a separate discipline — application lifecycle management (ALM) — promoting a report through Dev → Test → Prod without breaking what's live for people already using it. It requires Premium, PPU, or Fabric capacity; it isn't available on plain Pro.
Service → Workspace → Deployment pipelines → assign Dev/Test/Prod stages Deployment rules swap a data source or parameter automatically per stage Deployment pipelines + XMLA read-write together give you a real CI/CD flow
Production & Platform Specialization — optional, not the required endpoint
D4✓ mastered30 mintap ▸
External tools: DAX Studio & Tabular Editor
Desktop's UI hits a ceiling. DAX Studio shows you query plans and storage-engine timing so you can actually find what's slow; Tabular Editor lets you bulk-edit measures and model metadata far faster than clicking through the pane.
External Tools ribbon tab → launches the tool connected live to your open model DAX Studio → Query Plan / Server Timings to profile a slow measure Tabular Editor → C# scripting to bulk-rename or reformat dozens of measures at once
D5✓ mastered35 mintap ▸
VertiPaq Analyzer & the DAX Studio optimization workflow
VertiPaq Analyzer shows exactly which columns and tables are eating your model's memory — the first stop before optimizing a slow or oversized model. Pair it with Server Timings to see whether a slow measure is the storage engine or the formula engine.
DAX Studio → Advanced → View Metrics (VertiPaq Analyzer) Sort by column size to find the worst offenders — usually a high-cardinality text column Server Timings tab → run the measure → compare Storage Engine (SE) vs Formula Engine (FE) time
D6✓ mastered30 mintap ▸
XMLA endpoint & Tabular Editor scripting
The XMLA endpoint exposes a Premium or Fabric-hosted semantic model as a real Analysis Services database — the door that lets Tabular Editor, DAX Studio, and CI/CD pipelines connect and edit it directly, at scale, outside Desktop entirely.
Fabric/Premium workspace → Settings → Premium → enable the XMLA endpoint (Read-Write) Tabular Editor → File → Open → From DB → paste the XMLA endpoint URL C# script to bulk-edit measures: foreach (var m in Model.AllMeasures) { m.FormatString = "#,##0"; }
D7✓ mastered30 mintap ▸
Fabric integration & Dataflows Gen2
Microsoft Fabric puts Power BI on the same OneLake as Data Factory, Synapse, and notebooks. Dataflows Gen2 are Power Query pipelines that land cleaned data into that shared lake, so several reports and tools can reuse the same table instead of each re-cleaning their own copy.
Fabric workspace → New → Dataflow Gen2 Same Power Query experience, but output lands in a Lakehouse/Warehouse in OneLake Semantic models and notebooks can both read that same underlying table
D8✓ mastered25 mintap ▸
Paginated reports & the Power BI REST API
Paginated reports, built in Report Builder, are for pixel-perfect, print-ready output — invoices, regulatory forms — where a normal canvas won't do. The REST API automates the platform itself: triggering refreshes, managing workspaces, embedding, all from outside the UI.
Report Builder (separate app) → RDL-based paginated report → publish to a workspace REST API — trigger a dataset refresh: POST https://api.powerbi.com/v1.0/myorg/groups/{groupId}/datasets/{datasetId}/refreshes
D9✓ mastered30 mintap ▸
Administration & deployment best practices at scale
Once dozens of teams are publishing, someone has to own capacity, tenant settings, and governance — who can publish where, how large a semantic model is allowed to get, and how it refreshes without timing out or starving other workloads.
Admin portal → capacity settings, tenant settings, usage metrics Large semantic model storage format → lets a model exceed the default 1 GB limit; exact limits depend on your workspace's license/capacity (Pro, PPU, or Fabric SKU) — check current limits rather than assuming 1 GB is a hard ceiling for everyone Deployment pipelines require Premium, PPU, or Fabric capacity — not available on plain Pro
